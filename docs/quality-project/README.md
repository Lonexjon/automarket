# Проект: повышение качества обработки Telegram-объявлений

Дата: 2026-08-29
Задача: без платного AI на каждое сообщение сделать так, чтобы цена машины
в базе была ценой машины, а не первым взносом/ежемесячным платежом/случайным
числом из текста, и чтобы "выгодная цена" на сайте не врала.

Это не техническая документация по коду (она в самом коде и в
`docs/PROJECT_OVERVIEW.md`) — это разбор: что было не так, почему, что
сделали и как это проверили.

---

## 1. Как искали проблему

Не гадали, а прогнали реальные объявления из прода через текущий парсер и
посмотрели на его провалы: 939 сообщений, которые парсер либо не смог
обработать, либо обработал с подозрительным результатом. Разобрали их
вручную по причинам — получилось несколько чётких классов ошибок (ниже).

## 2. Что именно было сломано

### 2.1. Первый взнос принимался за полную цену
Самая частая и самая опасная ошибка. Объявление вида
`Chevrolet Cobalt 2019, boshiga 5000$, oyiga 300$, narxi 15000$` — раньше
регулярка ловила **первое** число похожее на цену ($5000) и записывала его
как `price_usd`. Машина за 15 000$ показывалась в базе как объявление
за 5000$ — то есть казалась фантастически выгодной, хотя это был просто
первый взнос по рассрочке.

**Почему это критично именно для deal_score**: одна такая ошибка не просто
портит одно объявление — она тянет вниз медиану всего сегмента
(марка+модель+год), из-за чего *другие*, честно оценённые объявления в том
же сегменте начинают выглядеть "дороже рынка", хотя рынок оценён неверно.

### 2.2. Знак доллара перед числом не ловился
`$22.700 kami bor` (доллар перед числом, с точкой как разделителем тысяч)
не совпадал с regex, заточенным под `22700$` после числа. Объявление
целиком пролетало мимо цены.

### 2.3. "Круглые" суммы без слова-валюты
`950ming`, `100 million` — без явного "сум"/"so'm" рядом эти числа не
распознавались как деньги вообще, хотя по контексту (узбекский рынок,
язык объявления) это очевидно сум.

### 2.4. Посты "продано" маскировались под активные объявления
Часть каналов пишет короткую приписку `#Sotildi` / "Poздравляем с
покупкой!" к уже проданной машине, либо публикует отдельный пост-подтверждение
продажи. Раньше это разбиралось как обычное объявление с ценой — то есть
проданная машина оставалась в живой ленте.

### 2.5. Машины старше 2000 года отбрасывались
Год парсился регуляркой с диапазоном 2000–2029 — любая машина 1970-х–1990-х
годов просто не проходила фильтр и терялась, даже если во всём остальном
объявление было нормальным.

### 2.6. (найдено уже в процессе фикса) Дубликаты объявлений держали устаревший deal_score
После того как ввели `price_type`/`needs_review`, скрипт `deal_score.py`
пересчитывал цифры только для "канонических" объявлений (не дублей, с
известными маркой и годом). Дубликаты и объявления без года просто не
попадали в цикл пересчёта — и если у них до этого случайно был выставлен
`deal_score` (по старой, ещё не расклассифицированной логике), он
оставался в базе навсегда, даже когда его цена на самом деле была первым
взносом. Поймано через health_check (см. ниже), который явно проверяет
такой инвариант.

### 2.7. Предупреждение о ненадёжной цене не доходило до ленты (фронтенд)
Уже после того как весь бэкенд был поправлен и задеплоен, при визуальной
проверке интерфейса (см. раздел 5) нашли ещё одну проблему: объявление с
`needs_review=true` (цена в тексте неоднозначна — например несколько
похожих на цену сумм) показывало число цены в ленте точно так же, как
надёжное объявление. Предупреждение "цена неоднозначна, проверьте
оригинал" существовало, но только на странице конкретного объявления —
до которой пользователь долистывает далеко не всегда. В ленте — самом
частом месте просмотра — сомнительная цена выглядела как обычная.
Исправлено: добавлен бейдж "⚠️ Требует проверки" прямо на карточке в ленте.

## 3. Как чинили (принцип, не список функций)

Не переписывали парсер с нуля и не подключали внешний AI на каждое
сообщение — усилили существующий:

- **Классификация денег по контексту, а не "первое похожее число"**: для
  каждой найденной в тексте суммы смотрим на ближайшее к ней слово-маркер
  (boshiga/бошига → первый взнос, oyiga/ойига → ежемесячный платёж,
  nasiya/rassrochka → рассрочка вообще, narxi/цена → скорее всего полная
  цена) и результат по каждой сумме получает свой тип:
  `full_price / down_payment / monthly_payment / exchange_addition /
  installment / negotiable / unknown`.
- **Никогда не подставлять первый взнос вместо цены.** Если уверенно
  определить полную цену не получилось — `price_usd = NULL`, а не
  "наименее плохая догадка".
- **Явная пометка неоднозначности** (`needs_review`), когда в тексте
  несколько чисел, каждое похоже на полную цену — вместо того чтобы
  выбирать одно из них наугад.
- **deal_score считается по железному правилу**, а не по эвристике:
  только `price_type == full_price AND needs_review == 0 AND` каноническое
  объявление (не дубль, есть марка и год) участвует в медиане сегмента и
  может получить свой собственный deal_score. Сегмент меньше 3 объявлений —
  deal_score не считается вообще (мало данных = не рынок, а случайность).
  Плюс два прохода по ценам: сначала грубая медиана, потом отсекаем
  статистические выбросы (цена меньше 35% от грубой медианы — почти
  наверняка сбой парсинга, а не реально дешёвая машина) и считаем чистую
  медиану уже по оставшимся.
- **Идемпотентная миграция схемы** — новые колонки (`price_type`,
  `price_confidence`, `needs_review`, `price_reason`) добавляются через
  `ALTER TABLE ... ADD COLUMN`, обёрнутый в try/except на случай, если
  колонка уже есть. Прогон скрипта повторно ничего не ломает.
- **health_check делит находки на critical/warning**, а не выдаёт одну
  простыню текста — так сразу видно, что реально сломано (например
  "у объявления с недостоверной ценой посчитан deal_score" — инвариант
  нарушен, это баг), а что просто информационная сводка (например
  количество объявлений с меткой "возможно продано").

## 4. Тесты

37 юнит-тестов (`python3 -m unittest discover -s tools -p "test_*.py"`),
включая регрессионные кейсы на реальные прод-ошибки:

- $15 000 машина с первым взносом $5 000 → в базе должна остаться
  `price_usd=15000`, а не `5000`.
- Ежемесячный платёж отдельно от первого взноса — оба не должны попасть
  в `price_usd`.
- Отрицание рассрочки (yo'q/йўқ/нет/emas рядом с nasiya/рассрочка) —
  не должно ложно помечать честную полную цену как installment.
- Несколько цен в одном объявлении (обмен + доплата) — доплата не
  становится ценой машины.
- Смешанный кириллица/латиница текст — парсинг не должен ломаться от
  смены алфавита в одном сообщении.
- Дубликат объявления со старым deal_score — обязан обнулиться при
  следующем прогоне, а не хранить устаревшее число вечно.

Все 37 — зелёные.

## 5. Проверка интерфейса (визуально, в браузере)

Раньше эта проверка не проводилась после деплоя бэкенд-части — только
синтаксическая проверка JS. В рамках этой папки прогнали реально:
локально поднят API (uvicorn) + отдан фронт через тот же процесс
(`app.mount("/", StaticFiles(...))`), в базу вручную вставлено 6 карточек,
покрывающих каждый сценарий (хорошая цена, дороже рынка, договорная,
только первый взнос, неоднозначная цена, маленький сегмент), открыто в
Playwright/Chromium.

Результат:
- лента корректно показывает бейджи "Хорошая цена -X%" / "Дороже рынка
  +X%" / "Цена не определена" — ни разу ложного "хорошая цена" на плохих
  данных;
- тёмная/светлая тема переключаются и сохраняются;
- страница объявления с `needs_review` показывает явное текстовое
  предупреждение "цена в тексте объявления неоднозначна";
- **найден и исправлен** пробел из п. 2.7 (предупреждение не доходило до
  ленты) — теперь исправлено и подтверждено новым скриншотом.

Скриншоты этой проверки не сохранены в репозитории (они лежат во
временной директории сессии) — при необходимости прогон легко повторить
тем же способом, шаги описаны выше.

## 8. Второй проход: полный редизайн интерфейса (2026-08-30)

Отдельная задача от владельца: сделать интерфейс похожим на настоящий
продукт (mobile-first, без ощущения админ-панели), на тех же четырёх
существующих эндпоинтах (`/v1/listings`, `/v1/listings/{id}`, `/v1/stats`,
`/v1/facets`) — backend и пайплайн не трогать.

### Что изменилось

Полностью переписаны `web/index.html`, `web/listing.html`, `web/common.js`,
`web/app.js`, `web/listing.js`, `web/style.css`:

- Компактная шапка (название, короткое пояснение, счётчик объявлений,
  время обновления, переключатель темы) вместо большого градиентного
  hero-блока.
- Фильтры (марка, модель, город, цена/год от-до, минимальный deal_score)
  живут в bottom sheet на мобильном / модалке на десктопе, со счётчиком
  активных фильтров, синхронизацией с URL (переживает переход на карточку
  и возврат назад), сбросом страницы на 1 при смене фильтра.
- Карточка: фото с fallback и lazy-loading, цена, объяснение deal_score
  (медиана + размер сегмента), до 2 предупреждений по важности, источник.
- `dealTrust()` в `common.js` — единственное место, где решается, можно ли
  показать бейдж "выгодная цена": блокирует его при отсутствии цены,
  price_type ≠ full_price, needs_review, низком price_confidence,
  критическом флаге или маленьком/отсутствующем сегменте. Сам deal_score
  нигде не пересчитывается, фронт только решает — показывать то, что
  посчитал backend, или нет.
- Детальная страница: галерея с fallback, объяснение deal_score простыми
  словами, таблица характеристик, флаги разделены по severity (разные
  цвета), кнопка перехода к оригиналу — с дублирующей закреплённой панелью
  внизу на мобильном.
- Новые состояния: ошибка API с кнопкой "Повторить", пустой результат со
  сбросом фильтров, страница несуществующего объявления, skeleton-карточки.

### Безопасность (XSS)

Раньше данные объявления (title, city, description_raw, labels флагов,
source_url) подставлялись в HTML-строки через `innerHTML`. Теперь весь DOM
строится через `el()` (`common.js`) — данные всегда идут как `textContent`,
никогда не парсятся как разметка. `source_url`/`photo_url` дополнительно
проходят через `safeUrl()`, который принимает только http/https и
отбрасывает всё остальное (`javascript:...` и т.п.) до того, как значение
могло бы попасть в `href`/`src`.

Добавлен `tools/test_web_xss.mjs` — отдельный regression-скрипт
(Playwright, Node ≥22, запускается вручную: `node tools/test_web_xss.mjs`):
поднимает реальный API на тестовой базе с HTML/JS-полезной нагрузкой в
каждом текстовом поле объявления и проверяет, что ни `alert()` не
срабатывает, ни один тег не оказывается в живом DOM как исполняемая
разметка.

### Найденные и исправленные баги

1. **CSS-специфичность `.filter-sheet` vs `[hidden]`** — оба селектора
   имели одинаковую специфичность, но `.filter-sheet { display: flex }`
   был объявлен позже в каскаде и перебивал `[hidden]`: панель фильтров
   оставалась видна, даже когда JS ставил `hidden=true`. Добавлено явное
   `.filter-sheet[hidden] { display: none }`.
2. **Приоритет операторов в строке даты карточки** — `a || b + c`
   выполнялось как `a || (b + c)`, из-за чего время публикации пропадало
   всякий раз, когда город/пробег были заполнены. Исправлено явным
   промежуточным вычислением.
3. **`price_confidence` — категория, а не число.** Реальные данные с
   прода показали `price_confidence ∈ {high, medium, low}` (см.
   `parsers/money.py`), а не число 0–1, как читался generic-тип `number` в
   `openapi.yaml`. Старая проверка `price_confidence < 0.5` тихо никогда
   не срабатывала для строки (JS сравнение строка/число даёт `false` без
   ошибки) — бейдж "выгодная цена" не блокировался этим условием вообще.
   Исправлено на `price_confidence === "low"` после проверки реальных
   значений через exec.yml.

### Production

Задеплоено через exec.yml (`git reset --hard origin/main` + `systemctl
restart automarket-api`) двумя коммитами (редизайн, затем фикс
`price_confidence`). Проверено на живом сервере: сервис `active`,
`index.html`/`app.js`/`common.js` отдаются, `/v1/stats` и `/v1/listings`
возвращают реальные данные (4366 объявлений), реальная форма
`price_confidence` на проде подтверждена до фикса и после.

**Ограничение честности:** сам продакшн-сервер (`45.76.32.57:8000`) не
имеет домена/TLS и слушает по чистому HTTP на нестандартном порту — эта
сессия работает через HTTPS-прокси и не может открыть его напрямую в
браузере ни отсюда, ни через WebFetch (оба варианта проверял, оба
отклонены). Browser-проверка (390×844, 1440×900, XSS, все состояния)
сделана на том же коде и против такой же схемы данных локально; сама же
продакшн-проверка после деплоя сделана через реальные HTTP-запросы к
сервису на VPS (`curl` изнутри самого сервера) — это подтверждает, что
задеплоенный код правильный и API отвечает, но не то же самое, что
открыть сам публичный URL в браузере, потому что такого URL с браузерным
доступом снаружи сейчас не существует.

### 8.1. Третий и четвёртый баг: найдены владельцем в реальном браузере (2026-08-30)

Владелец открыл `http://45.76.32.57:8000/` напрямую (порт открыт в ufw,
просто у этой сессии нет прямого сетевого доступа к произвольным IP —
см. ограничение выше) и прислал скриншот реального объявления
`tg_afdf96e1d5`. Это подтвердило ценность честной browser-проверки:
нашлись два реальных бага, которых не было в локальных фикстурах.

**Баг 3 — `money.py` не ловил маркер "как вариант" рядом с ценой.**
Текст объявления: `Нархи: Вариантга 500$ берса 15 ой 100$ дан беришга`
("цена: как вариант — 500\$, [или] за 15 месяцев по 100\$"). "Вариантга"
между меткой "Нархи:" и числом 500 не давало метке сработать (короткое
`LABEL_WINDOW`) — 500 резолвилось как непомеченный кандидат-одиночка и
уверенно становилось `price_usd=500, needs_review=false`. Сайт показывал
$500 как обычную честную цену для "идеального" Chevrolet 2010 года — хотя
по смыслу это часть схемы рассрочки, а не твёрдая цена. Добавлен новый
маркер `VARIANT_RE` ("вариант"/"variant") с узким радиусом (20 символов):
кандидат рядом с ним помечается `uncertain_variant` и больше не может
стать `price_usd`. Обязательный кейс "$15000 + первоначальный взнос
$5000" не пострадал (там маркер "первоначальный взнос" физически ближе к
другому числу, "вариант" в тексте не встречается вообще). Прогнан
`tools/reprocess_prices.py` по всей базе (6125 объявлений, изменилось 9,
из них 1 — цена превратилась в NULL задним числом). Новый тест
`test_variant_price_next_to_installment_is_not_a_confident_price` (38
тестов всего).

**Баг 4 — фронт не распознавал реальный severity критических флагов.**
`openapi.yaml` описывает `DealFlag.severity` как `info|warning|negative`,
но `parsers/regex_extract.py` реально шлёт `sold_mentioned` с severity
`"critical"` (контракт устарел относительно кода). `dealTrust()` в
`common.js` проверял только `severity === "negative"` — то есть на
реальных данных условие "не показывать хорошую цену при критическом
флаге" никогда не срабатывало ни для одного объявления. Добавлен набор
`CRITICAL_SEVERITIES = {"negative", "critical"}`, используется и в
`dealTrust()`, и при выборе иконки флага в `listing.js`.

Оба бага задеплоены (коммиты `9b8dc12`, `239607b`), проверены на живом
сервере: `tg_afdf96e1d5` теперь отдаёт `price_usd: null, price_type:
"monthly_payment", needs_review: true`.

### Осталось нерешённым

- У сайта нет домена/HTTPS — только IP:8000 без TLS. Из-за этого его
  нельзя открыть напрямую в браузере снаружи для финальной сверки "как
  видит пользователь" — нужен домен + reverse proxy (nginx/Caddy) с
  сертификатом, если это должно стать доступно реальным пользователям.
- Модель фильтруется точным текстовым полем (API не отдаёт список
  моделей, только марки/города через `/v1/facets`) — работает, но без
  автоподсказки; можно добавить facet по моделям на backend отдельной
  задачей, если понадобится.
